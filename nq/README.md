# jnats vs the NQ Java client: feature gap

This directory records which features of this client (jnats,
`io.nats.client`) the NQ Java client (`dev.nq`, generated by
[wallyqs/nq.dev](https://github.com/wallyqs/nq.dev) under `packages/java`)
does not provide. A jnats-compatible facade over NQ would have to fill these
gaps.

The method is read-only. The jnats public API was enumerated from source and
each feature was checked against the `dev.nq` sources, not only the
capability manifests. NQ takes its behaviour from oracles, so each gap also
records whether an oracle has the feature:

| Repository | Revision |
|---|---|
| jnats (this branch) | upstream `nats-io/nats.java` main `f74fc83` (2.26.5-SNAPSHOT) |
| NQ | `wallyqs/nq.dev` `e602352` |
| nats.go oracle | v1.54.0 (`7a8404a`, the commit pinned in `ir/spec/architecture.md`) |
| orbit.go oracle (batch publishing) | `8898afe` |

Nothing was run against a live server. Every finding comes from reading
source.

Detailed reports have one row per feature, with file:line references to
jnats, `dev.nq` and the oracle:

- [core.md](core.md): connection, options, subscriptions, dispatchers, messages, listeners and statistics
- [jetstream-management.md](jetstream-management.md): the JetStream context, stream and consumer management, publishing, and the API types
- [jetstream-consumption.md](jetstream-consumption.md): push, pull and ordered consumers, the simplified consumer API, and acks
- [kv-objectstore-services.md](kv-objectstore-services.md): Key-Value, Object Store, the service framework and utilities

## Summary

The NQ Java client covers almost all of nats.go. The capability manifests
list:

- 248/282 core symbols, where the 34 unsupported are Go channel, `context` and `net.Dialer` APIs;
- 117/121 services symbols.

For JetStream, the source implements nearly all of the nats.go `jetstream`
package, including KV and Object Store. It also implements all of orbit.go's
atomic and fast-ingest batch publishing.

Most gaps against jnats are therefore **jnats-only**: nats.go has no
equivalent. Under NQ's rules, each of these needs a facade decision rather
than IR derived from an oracle. The biggest gap is the legacy jnats
`JetStream.subscribe(...)` family, which NQ excludes on purpose
(`docs/JETSTREAM-PLAN.md:57`).

| Area | Gap rows (missing or partial) | Main point |
|---|---|---|
| [Core](core.md) | 73 (38 missing, 34 partial) | almost all gaps are jnats-only |
| [JetStream management and publishing](jetstream-management.md) | 29 | all 24 JSM calls and every stream/consumer config field are present |
| [JetStream consumption](jetstream-consumption.md) | 48 (21 missing, 24 partial) | the legacy `subscribe` family is missing by design |
| [KV / Object Store / services / utilities](kv-objectstore-services.md) | 50 (some rows record present-but-different) | the nats.go KV/OS/micro surface is present |

These are table rows. A row can group a few related options, so the counts
show relative size, not an exact feature count.

## 1. Gaps beyond NQ's JetStream oracle

NQ's JetStream oracle is the `nats.go/jetstream` package. Only the first
item below is in an oracle NQ uses (orbit.go). The rest match
`nats.go/jetstream` exactly: nats.go lacks them too. Some come from fields
the server sends that only jnats, or legacy nats.go (`jsm.go`), exposes.
Adding them would be a deliberate extension, checked against a live server
rather than nats.go.

- **Batch direct get** (`multi_last`, `up_to_seq`, `start_time`). The oracle is orbit.go `jetstreamext/getbatch.go`. 14–18 orbit symbols are correctly marked `planned`. No NQ target has it, and jnats 2.26 has only a flag and a constant.
- **First message by start time** (jnats `getFirstMessage(stream, ZonedDateTime[, subject])`). The server takes `start_time` in a message-get request (`server/jetstream_api.go:837`). The `nats.go/jetstream` request has only `seq`, `last_by_subj` and `next_by_subj` (`jetstream/stream.go:259-263`), and so does NQ's. orbit.go offers start time only for batch get.
- **Info fields the server sends but `nats.go/jetstream` drops:**
  - `StreamInfo.alternates` (`server/stream.go:353`; legacy `jsm.go:1059` only);
  - `StreamState.lost` (`server/store.go:183`; in no nats.go);
  - source and mirror `external` and `error` (`server/stream.go:481`; legacy `jsm.go:1075-1076` only).

  Each needs a field in the IR's info records.
- **`ConsumerInfo.calculatedPending`.** A jnats convenience, not a server field: `numPending + delivered.consumerSeq`.
- **Purge result.** The server replies with `purged`, and `nats.go/jetstream` decodes it (`stream.go:207`) but returns only an error, as NQ's `void` purge does. jnats returns a `PurgeResponse`. The count is already decoded in NQ, so this is the cheapest extension.
- **Typed direct-get result.** A direct get's `Nats-Num-Pending`, `Nats-Last-Sequence` and `Nats-Stream` headers stay in the raw header map, as in nats.go's `RawStreamMsg`. jnats `MessageInfo` exposes them as typed fields. NQ also has no generic `MessageGetRequest`, only fixed get methods.
- **Legacy `js.go` push/pull subscribe**, which nats.go has only in `js.go`, not in `jetstream/`. NQ already has `LegacyOrdered` internally (JetStream.java:5238), used by KV and Object Store, and could build on it.
- **Public JSON for config and info objects**, with nats.go enum names. The Go facade (`nq.go`) has it; no other target does.

## 2. jnats-only features (facade decisions)

- **Concurrency and API shape:**
  - the `CompletableFuture` request API and `requestWithTimeout`. Rust tokio, TypeScript and Python asyncio already have async requests in NQ, but Java does not;
  - `Dispatcher`: many subscriptions on one thread, a default handler, per-subject unsubscribe;
  - executor and thread-factory injection.
- **Listeners:**
  - a single `ConnectionListener` with `RESUBSCRIBED` and add/remove;
  - typed `ErrorListener` methods: `errorOccurred`, `messageDiscarded`, `socketWriteTimeout`, `pullStatusWarning`/`Error`, `heartbeatAlarm`;
  - `ReadListener`, `TimeTraceLogger`, `traceConnection`.
- **Statistics:** 11 extra counters (pings, oks, errs, exceptions, dropped, requests/replies/duplicates/orphans, flushes, outstanding), `StatisticsCollector`, and advanced stats.
- **Outgoing queue:** `maxMessagesInOutgoingQueue` and discard-when-full, `writeQueuePushTimeout`, `outgoingPendingMessageCount`, `flushBuffer`.
- **Socket and wire options:**
  - `socketReadTimeout`, linger, `SO_RCVBUF`/`SO_SNDBUF`, `java.net.Proxy`;
  - `maxControlLine`, `hostnameResolveMode`;
  - the CONNECT flags `noHeaders`, `noNoResponders` and `clientSideLimitChecks`;
  - strict subject validation.
- **Configuration:**
  - `Options.Builder` and `Properties` file config;
  - `ForceReconnectOptions` (forceClose, flush wait);
  - pluggable `ServerPool`, `DataPort` and `SSLContextFactory`;
  - keystore paths and passwords, `opentls`.
- **Messages:**
  - the `Headers` class;
  - `isStatusMessage`/`getStatus`, `getSubscription`, `getSID`, `getConnection`;
  - JetStream: `isJetStream`, `lastAck`, `consumeByteCount`, `nakWithDelay(Duration)` (NQ takes nanoseconds).
- **JetStream context:**
  - `publishNoAck`, `optOut290ConsumerCreate`;
  - client-side server-version gating and public `ServerVersion` comparisons;
  - `MessageTtl.never()` and custom TTL strings;
  - the direct-get header constants and `DEFAULT_API_PREFIX`.
- **Simplified consumer API:**
  - a user `Dispatcher` for `consume`;
  - fetch options: byte and message limits combined (`FetchConsumeOptions.max`), `noWaitExpiresIn`, `thresholdPercent` and `raiseStatusWarnings`;
  - lifecycle: `isStopped`/`isFinished`, `AutoCloseable`, `getConsumerName`;
  - JSON (de)serialisation of the options.
- **Legacy subscribe options:** bind and fastBind, `messageAlarmTime`, pending limits, deliver group, `JetStreamReader`, and stream lookup by subject.
- **Key-Value:**
  - `put(key, Number)`, `getValueAsLong`/`getValueAsString`;
  - `getDataLen` (Nats-Msg-Size with META_ONLY), `getConsumerNamePrefix`;
  - a public `KeyValueEntry(Message)`;
  - a push-callback watcher (NQ's watcher is pull-based), the `consumeKeys` queue, and filtered `keys(...)` lists.
- **Object Store:** `updateMeta`/`delete` return `ObjectInfo` and `seal` returns a status; NQ returns `void`.
- **Services:**
  - the `Discovery` client, left out on purpose (`docs/SERVICES-PLAN.md:54`);
  - per-endpoint dispatchers, stats suppliers and start time;
  - drain timeout, a non-draining stop, and the `startService()` future;
  - JSON-parseable response objects and `getPingResponse()`.
- **Utilities:** public `NKey`, `NUID`, `Validator`, the JSON utilities, `Digester`, `ServerVersion` and `Encoding`. NQ keeps all of them internal.

## 3. Behaviour differences a facade must translate

- **Sync request failure:** jnats `request` returns `null` on timeout or no-responders. NQ throws `NqException` (`timeout` or `no_responders`).
- **`next()` timeout:** jnats returns null; NQ throws.
- **Reconnect buffer overflow:** jnats drops and counts the message. NQ, like nats.go, throws `reconnect_buf_exceeded`.
- **TLS:** NQ always verifies the server hostname (`TlsTransport.java:34`, endpoint identification `HTTPS`). jnats does not set endpoint identification (`impl/SocketDataPort.java:142-160`).
- **Defaults:**
  - inbox prefix: jnats `_INBOX.`, NQ `_INBOX`;
  - pending limits: jnats 500,000 messages (65,536 for sync subscriptions), NQ 512Ki;
  - subjects: jnats allows UTF-8, NQ allows ASCII;
  - pull thresholds: jnats 25%, NQ absolute counts at 50%.
- **Exceptions:** jnats uses checked `IOException`/`JetStreamApiException`; NQ uses unchecked `NqException` with `code()`.
- **Acks:** acking twice in jnats is a no-op; NQ throws `MSG_ALREADY_ACKD`.
- **`stop()`:** jnats `stop` corresponds to NQ `drain()`; NQ `stop()` discards buffered messages.
- **Pinned consumers:** jnats refuses fetch and next on them; NQ allows both.
- **Push flow control:** NQ does not answer `Nats-Consumer-Stalled` heartbeats, which matches nats.go `jetstream/push.go`.
- **Message deletion:** jnats `deleteMessage(stream, seq)` erases the message by default, which is NQ `secureDeleteMsg`. NQ `deleteMsg` matches `deleteMessage(stream, seq, false)`.
- **Object Store:**
  - `putFile` names the object by its full path in NQ, by the file name in jnats;
  - `list()` on an empty store throws `NO_OBJECTS_FOUND` in NQ and returns an empty list in jnats.
- **Service handlers:** when a handler throws, jnats replies with a 500 error (`service/EndpointContext.java:83-89`), counts it and keeps serving. NQ now does the same (see §5.2), except that it sends no second reply when the handler had already responded. The 500's description is the exception's message (jnats sends `toString()`).

## 4. Where NQ Java is ahead of jnats

- orbit.go atomic batch publishing (`BatchPublisher`, `publishMsgBatch`) and fast ingest (`FastPublisher`). jnats 2.26 has only the constants, stream flags and the batch fields on `PublishAck`.
- Typed message-scheduling publish options (`withSchedule*`), publish retry and stall options, and async publish limits.
- `createOrUpdateStream`, `streamNameBySubject`, push-consumer management, `termWithReason`, and `Stream.unpinConsumer`.

## 5. Problems found in nq.dev, now fixed

All three are fixed on `wallyqs/nq.dev`: the error codes on `dev` (`cefee41`), the other two on branch `claude/blissful-shannon-znjm2g` (`dda5e6c`, rebased on `dev`).

1. **Fast-batch error codes (bug, fixed).** NQ copied orbit.go `jetstreamext/errors.go:35-38`, which assigns 10203–10206 to the fast-batch errors. nats-server's own codes are 10205–10208 (`server/errors.json`, `JSBatchPublish*Err`, v2.14.0 and v2.15.0); 10203 and 10204 are its message-schedule and consumer-reset errors. Measured on nats-server v2.15.0: a fast batch to a stream without `allow_batched` is refused with err_code 10205 "batch publish is disabled", and orbit.go's `errors.Is` reports it as `ErrFastBatchInvalidID`. NQ now uses the server's codes in all twelve profiles, recorded as a declared divergence from orbit.go. jnats (`support/NatsJetStreamConstants.java:205-208`) already agrees with the server.
2. **Service handler exceptions (fixed).** This report first said NQ "neither replies nor counts the error". Running the old code shows it was worse: the exception reached the connection's async error handler, whose service wrapper counted an error and **stopped the whole service**. NQ now answers jnats-style in Java, Python, Ruby and TypeScript, through new IR roots `svc_handler_failed` and `svc_responded`. The 500 error response carries the failure's text, or "handler failed" when there is none. The request counts as one error recording `500:<text>`, and the service keeps serving. Go and Rust handlers still panic, as in nats.go, and a C handler cannot fail. `TestServicesHandlerFailure` checks this live on the seven profiles.
3. **Capability manifests (overstated here; reason text fixed).** The JetStream reports below say roughly 270 Java `planned` entries are stale. That was wrong. Under nq.dev's rule, `implemented` needs a test that exercises the binding against the oracle:
   - Record types and fields stay `planned` by design.
   - Most of the Go-shaped symbols (listers' `Err`/`Name`, `With*` option functions, `JSErrCode*`, Go `String`/`MarshalJSON`) have no exercised Java binding.

   What *was* stale is the reason text, which still read "awaiting IR" for milestones that have all landed; it now says why each entry stays planned. Java's stream-level `PauseConsumer`/`ResumeConsumer`/`ResetConsumer`/`ResetConsumerToSequence` were implemented but unexercised. They now have evidence and are promoted, so Java's JetStream manifest is 398 implemented, up from 394. Read the "stale manifest" sections of the detailed reports with this correction in mind.

## Suggested order for a jnats-compatible facade

1. **Thin translation layer:** null-on-timeout, checked exceptions, `Options.Builder` mapped onto `dev.nq.Options`, a `Headers` class over the header map, and the listener adapters. This is shell-only.
2. **`Dispatcher` and the `CompletableFuture` request.** Other NQ targets already have async requests to model this on.
3. **Behaviour that changes wire, statistics or policy:**
   - CONNECT flags, extra counters, outgoing-queue limits, `maxControlLine`, strict validation, resolve mode, force-close, drop-on-overflow;
   - the JetStream extensions in §1.

   Each needs IR, vectors and a recorded divergence where it departs from nats.go.
4. **Legacy `JetStream.subscribe`**, if the facade has to support it. It is the largest single block, and its only oracle is nats.go `js.go`.
